# World Authoring Guide — how to modify a district and get it into the game

The **day-to-day workflow doc** for `assets/world_source/` — the real commands an artist runs to
change a district `.blend` and see it in-game. The decided naming/structure conventions live in
[`BLENDER_CONVENTIONS.md`](../../BLENDER_CONVENTIONS.md) (repo root); this file is about *doing*.

---

## 1. Pipeline map (what happens between Blender and the game)

```
assets/world_source/pieces/Piece_<gx>_<gy>.blend                  ← the Blender source you edit
        │  blender/tools/export_world.py (glTF, drops Blender-only collections)
        ▼
src/main/resources/com/openworld/world/districts/<stem>.gltf/.bin    ← throwaway intermediate
        │  WorldBaker (Java, named markers → gameplay nodes)
        ▼
…/districts/<stem>.tscn                                              ← the streamed scene
        │  NavBaker (pedestrian navmesh from the scene's own collision)
        │  DistrictBinaryConverter (.tscn → sibling .scn, faster stream-in parse)
        ▼
streamed in-game by the master's WorldZoneMarkers (predictable path — the master
never needs re-baking when a district changes)
```

**One command runs all of it:** `blender/tools/build_piece.sh` (from `assets/world_source/`) — bake-only,
exports/bakes the district's `.blend` exactly as currently saved (see §3):

```bash
blender/tools/build_piece.sh Piece_1_1
```

Walk-test one district: `<godot-jvm> --path <repo> res://src/main/resources/com/openworld/world/hosts/SoloPiece.tscn`
(the build points it at the piece you just built). Full world: `hosts/WorldMaster.tscn`.

## 2. Every district is hand-owned — there is no generator to run

All 39 districts are **permanently hand-authored/hand-edited directly in Blender**. The old
per-district generator (`towns/districts/build_district.py` — PLATEAU import + procedural filler,
driven by a `CONFIG` dict) was removed outright: there was no documented or code-level workflow
that ever re-ran it across multiple districts to propagate a fix, its "recycled" (procedural
filler) districts' building layout wasn't even reproducible run-to-run (Python's per-process
string-hash randomization fed the placement seed), and every regen trigger in this pipeline was
already single-district and artist-initiated. If a district's ground, roads, or buildings ever
need to change, that happens by editing the `.blend` directly in Blender (or through the
`road_kit_authoring` addon for roads specifically, §7) — the same way `MANUAL` content always
worked, now the way *everything* works:

| Collection | Contents | Changes how? |
|:--|:--|:--|
| `STREET` | buildings, terrain/ground, roads (visual + collision) | **hand-edit directly in Blender** |
| `MARKERS` | lane/route/seam/spawn empties | **hand-edit directly in Blender** |
| `MANUAL` | hand-authored content (roads, water/spawn/instance markers) | **hand-edit directly in Blender** |
| `NEIGHBOR_REF` | linked neighbour-district context (§4), never exported | regenerated by `blender/tools/link_neighbors.py`, read-only either way |

Nothing here is ever wiped or regenerated by a script anymore — there's no longer a meaningful
distinction between "generated" and "hand-authored" collections in terms of durability, only in
terms of *what kind of content they conventionally hold*. Kept as separate collections anyway
(cheap, and it preserves the intent-signaling: `STREET`/`MARKERS` for ground/terrain/base roads,
`MANUAL` for what you personally placed) rather than merged into one — the collections stay
distinct for readability, not because the tooling needs them to: the world-session tooling below
syncs **every** top-level collection a district has (whatever it's named — `STREET`, `MARKERS`,
`MANUAL`, or anything added later), nested under one `Piece__<id>` wrapper per piece, not
a fixed `MANUAL`-only allowlist (`blender/lib/session_common.py`'s `EXCLUDE_COLLECTIONS` denylist — just
`NEIGHBOR_REF`, §4's read-only linked reference content, and Blender's always-empty default
`Collection` — is the only thing ever left out).

**PLATEAU import itself (`blender/lib/plateau_import.py`, `plateau/extract_plateau.py`) was removed too**
— once the Rainbow Bridge overlay, Haneda airport, and the recycled-building-kit curator had each
produced their output artifact (`pieces/Piece_2_3_b.blend`, the bridge,
`buildings/PLATEAU_RainbowBridge.blend`, `buildings/PLATEAU_HanedaTerminal.blend`,
`buildings/RecycledBuildingKit.blend` — all already committed), the generator scripts that made
them (`overlays/build_rainbow_bridge_overlay.py`, `blender/buildings/build_haneda_airport.py`,
`blender/buildings/build_rainbow_bridge.py`, `blender/buildings/build_recycled_kit.py`) had done their one-time
job too, same as the per-district generator — so they were removed along with the PLATEAU
import/extraction library they all shared. Nothing left in this pipeline reads raw PLATEAU/CityGML
data anymore; every PLATEAU-derived asset that exists is now a permanent, hand-owned `.blend`, no
different from a hand-modeled one. If real PLATEAU data is ever wanted again in the future (a new
district, a new landmark asset), that means re-writing an import script from scratch against the
raw CityGML source (`/data/danilko/plateau_model/`, see `plateau/ATTRIBUTION.md`) — there is no
turnkey extraction/import tool left in this repo to reach for.

## 3. The one build loop (bake-only)

```bash
cd assets/world_source
blender/tools/build_piece.sh Piece_1_1     # exports/bakes the .blend exactly as currently saved
```

Exports → bakes → navmeshes → refreshes the `.scn` for whatever is currently saved in that
district's `.blend` — never regenerates anything. `DistrictBinaryConverter` mtime-skips untouched
districts, so a freshly baked `.tscn` is never shadowed by a stale sibling `.scn` — nothing else
to remember. Streaming resolves districts by predictable path, so **the master never needs
re-baking for a district change** (`blender/tools/build_world.sh` is only for grid/theme/arterial-level
changes, or after marking a cell void/not-void in `MAP` — §4 "Add/remove whole districts").

## 4. Editing across district borders (multi-district connections)

### One file for the whole world (world_session.blend) — the default way to edit

You should not need to track which of 36+ per-district `.blend` files is which, or open them one
at a time, for day-to-day road/zone/landmark authoring. Open the persistent whole-world session
instead:

```bash
cd assets/world_source
blender --background --python blender/tools/open_world_session.py --      # first run: creates it
blender assets/world_source/world_session.blend                   # then open it normally
```

This is every registered piece's content — grid district or freestanding piece alike, no
distinction — `MANUAL` (roads, water/spawn/instance markers, hand-placed landmarks) **and**
`STREET`/`MARKERS` (ground/terrain, since nothing regenerates them anymore, §2), or a
freestanding piece's own `OVERLAY`/`MANUAL` content (a bridge/highway/rail line living outside
any grid cell, §5) — appended (not linked — genuinely editable) into ONE stable file. Each
piece's collections nest under its own `Piece__<id>` wrapper at its registered `position`
(`blender/lib/piece_registry.py`; a grid district's happens to have been computed via
`world_grid.py`'s `district_center`/`elev_at` at migration time) — a freestanding piece like the
bridge gets **no additional coordinate shift**, since it's already authored in true world space
(§5), so it lands in the session exactly where it already sits relative to every piece around it.
Fly the viewport anywhere and edit any piece's roads, ground/terrain, water/spawn/instance
markers, hand-placed landmarks, **or a freestanding piece's own geometry** directly — the addon's
"Jump to District" (Road Kit panel, or `rka.jump_to_district`) searches every registered piece by
id and snaps the view there.

**Re-running `open_world_session.py` refreshes it in place**, not from scratch: it adds any
newly-built piece not yet in the session and prunes any piece that became void (grid cells only)
or got deregistered/deleted — without ever touching a wrapper already present (which may hold
edits you haven't written back yet). If an item with unsynced edits is about to be pruned, the
refresh aborts with nothing saved rather than silently discarding your work — write it back
first, or pass `--hard-resync <item>`/`--force-drop <item>` to deliberately override (`<item>` is
any registered piece id).

**Editing here is live-tracked, not diffed after the fact.** The addon marks a district dirty the
instant you actually edit something in it (Blender's own `depsgraph_update_post` change
notification — the same mechanism a real engine's world-partition/streaming-level editor relies
on to know what needs saving; see `session_dirty.py`), not by comparing content hashes after the
fact. Writing back only touches what's actually dirty:

```bash
blender --background assets/world_source/world_session.blend \
    --python blender/tools/writeback_world_session.py -- [--force-all] [--dry-run]
```

`--dry-run` reports which items are dirty without touching anything. Default writes back only the
dirty ones — for each: `writeback_district_group.py`'s per-item write, then `build_piece.sh`
(handles any piece uniformly now, grid or freestanding), then `check_seams.py` for every adjacent
**grid** pair touching a changed district (even if the *neighbour* itself wasn't edited — a moved
boundary object can still break a seam with an unchanged neighbour; a freestanding piece never
seam-pairs this way — it has no `.seam.json`, §5 — and is simply skipped by this check).
`--force-all` bypasses the dirty filter
for an explicit "export everything" pass. From the addon panel: "Open/Refresh World Session",
"Write Back Changed" / "Write Back All", same background-subprocess pattern as "Export District to
Godot" — watch the System Console.

`world_session.blend` is a working session, not a source of truth (each district's own `.blend`
still is — see "Reconciled staging file, not canonical merge" below) — it's gitignored, never
commit it.

**Not covered by this session, on purpose:**
- **World-level markers** (`region_<stem>` RegionConfig tuning, `slot_<landmark>` hero-district
  anchors) live only in `world_master.blend`, never in a district file, and that file is
  unconditionally regenerated from scratch on every `build_world.py` run — so even if you hand-
  edited one there today, it would be silently wiped on the next master rebuild. This is a real,
  separate, not-yet-solved gap, not something the world session reaches around.
- **Removing an existing district for real** has a one-click path now — the addon's "Remove
  Piece" (§4 "Add/remove whole districts (void cells)" below) deletes it and refreshes this
  session automatically. **Authoring a genuinely new district** (one that's never existed) still has no
  one-click path — there's no `CONFIG`-driven generator anymore (§2), and no PLATEAU import
  tooling left either (§6) — so it means building it by hand in Blender from scratch, or
  re-writing an importer against the raw CityGML source first. A deliberate authoring action
  either way, not something this session reaches around.

#### Reconciled staging file, not canonical merge

Each district's own `.blend` stays the real source of truth for **all** its content (`MANUAL`,
`STREET`, and anything else, §2) — `world_session.blend` is a synced working copy, not a
replacement for the per-district files. This was a deliberate choice, not a shortcut: Godot's own
zone streaming needs 39 independent export units regardless of how Blender-side authoring is
organized, and Blender has no `.blend` merge/diff tooling at all. Making the merged file canonical
(instead of a reconciled copy) would turn every edit anywhere in the world into a single shared-
file collision point, for a pipeline whose existing tooling (`build_piece.sh`'s stem-form bake-
only mode, `.seam.json` per stem) is entirely built around one-district-one-file ownership. The
world session gets you the "edit anywhere in one file" experience without that risk.

### When you already know exactly which 2-4 districts need a seam fixed

For a narrow "these two districts don't meet" fix, `blender/tools/open_district_group.py`/
`writeback_district_group.py` (below) still work the same way, scoped to just the districts you
name, in a disposable timestamped scratch file instead of the persistent whole-world one. Good
for a quick, contained fix; the world session above is the better default otherwise.

Districts are **collaged from different real PLATEAU locations** (different wards, even Osaka), so
adjacent borders do **not** naturally continue into each other — ground height, road ends and
building fabric all change at the seam. That is by design (a "greatest hits" map, not literal
geography); the model for what must line up:

- **Inter-district travel is carried by the always-resident master layer** — the arterial backbone
  + its collision deck (`ARTDECK`), and (planned) highway/train overlays (§5). Districts do
  **not** have to road-match each other edge-to-edge. (There is deliberately no world-spanning
  safety floor anymore — see "No world-spanning safety floor" below.)
- **A district's job at its border** is visual harmonization: its terrain/ground should meet the
  neighbour's without cliffs/z-fighting where players can see it, and not poke up through the
  arterial deck. Its internal roads may simply end near the border (traffic despawns at route end).
- The only *hard* cross-district contract is the generated seam-route empties (`seam_*`,
  `emit_seam_routes`) — regenerated automatically; you never hand-maintain them.

### See the neighbours while you edit (link_neighbors.py)

You no longer need to merge districts to fix a border. Link the adjacent pieces **into** the
district you're editing, as read-only referenced context at their true relative offsets:

```bash
cd assets/world_source
blender --background pieces/Piece_1_1.blend \
    --python blender/tools/link_neighbors.py -- --master
```

Then open `pieces/Piece_1_1.blend` normally and edit. What you get:

- A `NEIGHBOR_REF` collection with the 4 edge-adjacent districts' `STREET` content (add
  `--diagonals` for all 8, or `--all-districts` for **every** built district in the world, not
  just neighbours — useful once you're hand-authoring intersections/segments and want the whole
  assembled world as visual reference, not just the immediate border) placed at ±504 m and the
  correct theme-elevation delta — the **same numbers the runtime uses**, so what lines up in the
  viewport lines up in-game.
- `--master` also links the master's `ARTDECK` (arterial deck) so you can see exactly where the
  always-resident road layer crosses your border (`--master=ARTDECK,HARBOR` for more collections).
- The links are **true Blender library links**: read-only (you can't accidentally edit a
  neighbour), near-zero file-size cost, and **live** — rebuild or hand-edit a neighbour and the
  reference updates on next file open. They survive this district's own rebuilds, are dropped by
  every export automatically, and `-- --clear` removes them.
- To fix the *other* side of a seam, open the neighbour's `.blend` (run `link_neighbors.py` on it
  too) — each file only ever edits its own content.

### Inspecting without editing

- **`world_master.blend` itself now shows the real world.** The master build
  (`blender/tools/build_world.py`) library-links every **built** district's `STREET`/`MANUAL` into
  `LAYOUT` as a `Piece_<gx>_<gy>` collection-instance at its true world position — the same
  live-link mechanism as `link_world.py` below — replacing the old theme-coloured `Plate_*`
  preview boxes (a plate now appears only as the placeholder for a district not built yet).
  Opening the master shows the assembled world; edits still always happen in each district's
  own `.blend` (links are read-only), and `export_world.py` drops `LAYOUT` so none of it ever
  reaches the baked master — each district streams in on its own at runtime.
- **`blender/tools/link_world.py` → `world_overview.blend` — the whole world, persistently.** One
  re-runnable file linking **every built district** (`Piece_<gx>_<gy>` collection-instance
  empties at their true `district_center` + theme elevation), the master's `MARKERS` (+`ARTDECK`
  when a `--full` master built one), and every registered freestanding piece (e.g. the bridge,
  `Piece_2_3_b`). Regenerate with
  `blender --background --python blender/tools/link_world.py`; open `world_overview.blend` any time
  after. Because these are **live library links**: edit + save a district source `.blend`, reopen
  the overview (or File ▸ External Data ▸ Reload), and the edit is there — no rebuild. Content
  edits always happen in the district's own file (links are read-only here). **Moving a `Piece_*`
  empty is visualization-only** — runtime positions come solely from
  `blender/lib/world_grid.py:district_center` (the single source of truth), and every re-run snaps the
  empties back.
- `blender/tools/build_debug_preview.py` — same mechanism for an ad-hoc subset (a specific seam pair)
  into a throwaway `.blend`: 
  `blender --background --python blender/tools/build_debug_preview.py -- _debug_edge pieces/Piece_1_1.blend:1:1 pieces/Piece_0_1.blend:0:1`
- `blender/tools/render_cluster.py` — same idea as a top-down PNG render.
- `blender/tools/check_seams.py` — engine-free `.seam.json` cross-check of the generated seam routes.
- Headless smoke signal for streaming/traffic health: run `hosts/WorldMasterDebug.tscn` headless and
  watch for `N cars, M moving, K routed` (routed-but-0-moving = something fell through the ground).

### Fixing a border, step by step

1. `link_neighbors.py -- --master` on the district, open it in Blender.
2. Judge the mismatch at the shared edge (ground step? building clipping the deck? road stub
   pointing into a neighbour's building?).
3. Fix on **this** side only: sculpt/patch this district's terrain border band, add a hand ramp or
   retaining-wall mesh in `MANUAL` (with a `-colonly` proxy if it needs collision), or move/trim
   the offending generated content (then bake-only).
4. `blender/tools/build_piece.sh Piece_<gx>_<gy>` — bake-only, exports/bakes whatever you just saved.
5. Walk-test via `SoloPiece.tscn`, or the seam itself in `WorldMaster.tscn`.

### When roads/geometry must be edited across the seam together (open_district_group.py)

The step above assumes each side of a seam can be fixed independently, seeing the other only as
read-only reference. That's usually true for terrain (theme-step + taper already reconciles
elevation, §6) but road content is now standardly hand-authored (`ops_intersection.py`/
`ops_segment.py`, landing in `MANUAL` — the same workflow Piece_5_1's (industry) road content
was hand-built with) as real local mesh/curve geometry. Neither `link_neighbors.py`'s read-only
links nor Blender's Library Override system can edit linked mesh/curve vertex data — so if two
districts' roads genuinely need to be reshaped *together* (not just judged against a read-only
reference), use this instead:

```bash
cd assets/world_source
blender --background --python blender/tools/open_district_group.py -- \
    _edit_session_1_1_2_1 Piece_1_1 Piece_2_1
```

This APPENDS (not links) every top-level collection each named district's own `.blend` actually
has (`MANUAL`, `STREET`, `MARKERS`, and anything else — see §2's `EXCLUDE_COLLECTIONS` denylist
note above) into one disposable scratch `.blend` (`<out_name>.blend`), each shifted to its true
relative world offset (same `district_center`/`elev_at` numbers as every other tool here) and
nested under its own `Piece__<id>` wrapper collection. Because it's a real local copy, not a
link, every road/ground piece from every named district is simultaneously selectable and editable
— Edit Mode, live-edit dragging, snapping a segment's `port_*`/`arm_*` endpoint to meet a
neighbour's, reshaping terrain across a seam, all work normally, across district boundaries, in
one viewport.

When you're done, write the results back into each district's own `.blend`:

```bash
blender --background --python blender/tools/writeback_district_group.py -- _edit_session_1_1_2_1 --dry-run
blender --background --python blender/tools/writeback_district_group.py -- _edit_session_1_1_2_1
```

This un-shifts each district's content back to its own local coordinate frame and replaces that
district's collection(s) wholesale (one Blender subprocess per district, so files are never
opened/saved except one at a time). Then rebuild + re-validate as usual:

```bash
blender/tools/build_piece.sh Piece_1_1
blender/tools/build_piece.sh Piece_2_1
python3 blender/tools/check_seams.py pieces/Piece_1_1.seam.json pieces/Piece_2_1.seam.json
```

(`check_seams.py` always takes exactly the two `.seam.json` paths for one adjacent pair — it
doesn't sweep the whole grid on its own.)

The scratch `.blend` is a disposable working session, not a source of truth — never git-track it;
discard it once the write-back + rebuild is done. Re-running `open_district_group.py` any time
starts a fresh session from each district's current saved state.

### Add/remove whole districts (void cells) — for a less blocky landmass/harbor shape

The 6x6 grid (`blender/lib/world_grid.py`'s `MAP`) requires every `(gx,gy)` cell to be a real theme
keyword today — every cell is always either a built district or a "not built yet" placeholder
plate, never genuinely *absent*. That makes the world's outline exactly as blocky as the grid
(today's whole south row is `harbor`, i.e. one dead-straight coastline) — there's no way to open
a bay, add an island gap, or otherwise make the macro landmass shape less rectangular, short of
building a real (themed) district at every cell regardless.

**Mark a cell `void` in `MAP` instead of a theme keyword** to make it deliberately, permanently
absent — no placeholder plate (unlike "not built yet"), no `Piece_*`/`Plate_*` in
`world_master.blend`, no `region_*` marker (no AI spawns, no traffic, nothing streams there ever):

```python
MAP = [
    ...
    "void   resid  city   city   resid  rural",     # gy=3 -- (0,3) is now open water/gap
    ...
]
```

Then re-run `blender --background --python blender/tools/build_world.py` — the summary line's `void=N`
count confirms it, and `world_master.blend` shows nothing at all at that cell.

**There is deliberately no runtime toggle for this anymore.** An earlier version had a
`void_overrides.json` sidecar + an addon "Toggle Void" button so a cell could be flipped without
touching `MAP`'s source text; that was retired once the piece registry (`pieces.json`,
`lib/piece_registry.py`) became the single source of truth for what exists — marking a grid cell
`void` is now purely a `MAP`-source-text decision (hand-edit it, above), same weight as any other
world-design change. **This is a different operation from removing an already-built district's
content**, which is a piece-registry decision, not a `MAP` one: the addon's **"Remove Piece"**
(Road Kit panel > Pieces) permanently deletes a piece's `.blend` + its `pieces.json` entry and
rebuilds the master — use that to take an existing district out of the world; use `MAP`/`void`
(above) to declare a grid cell should never even show the "not yet built" placeholder in the
first place. ("Unload Piece", right above it in the panel, is neither of these — it only drops a
piece from your *currently open* session file, nothing on disk changes; see "One file for the
whole world" above.)

**What this does NOT do:** a void cell is still 504 m² and grid-aligned — you get a less blocky
*macro* shape (which whole cells exist), not a smooth/diagonal coastline at any finer resolution.
For organic-looking shoreline detail *inside* a real (non-void) border district, hand-author it
the same way any other border fix already works (see "Fixing a border, step by step" above): add
terrain/water geometry to that district's own `MANUAL` collection (a `water_<id>` marker for a
swim volume, §8; a hand-sculpted terrain patch for a curving bank) — this is already fully
supported per-district, no blocker, no pipeline change needed. Void cells (macro shape) + hand-
authored coastline detail in the districts bordering them (micro shape) together are the complete
answer — there's no need for sub-grid resolution or a non-uniform mesh.

**Seam data for existing districts is frozen, not live.** Each district's `.seam.json` (and the
seam-route empties in its own `MARKERS` collection) were computed once, when that district was
originally generated, via `world_grid.py`'s `is_void`/`elev_at`/`seam_route_name` primitives — the
convenience function that wrapped them (`build_district.py`'s `emit_seam_routes`, which already
tolerated a void neighbour the same as an off-grid one) no longer exists, since the whole
generator was removed (§2). Marking a neighbour void in `MAP` does **not** retroactively update an
existing district's already-baked seam markers — `blender/tools/check_seams.py` would flag the resulting
mismatch if run, but nothing currently re-syncs it automatically; fixing a stale seam is a hand
edit in Blender like everything else now. A hand-written script authoring a genuinely new district
in the future would need to compute its own seam data the same way, reusing those same
`world_grid.py` primitives directly (they're still there — only the wrapper function is gone).
The Godot runtime needs **no changes at all** for the void mechanism itself — `WorldZoneManager`
has no hardcoded grid-count anywhere; a missing marker simply means nothing streams there.

**No world-spanning safety floor.** `build_world.safety_floor()` (`--with-floor`) and the
per-district `add_ground_safety_plane()` (on by default for any non-fully-DEM-covered district)
were both removed outright — a collision-only floor sitting a meter or more below visual ground
silently trapped `Character`/`Player` bodies with no recovery path (neither has any
fall-out-of-world safety net, unlike vehicles, which `WorldZoneManager.maintainTraffic` reclaims
below `Y = -30`). Falling off a road, off the ArtDeck, or into a void cell now falls straight
through — same as any other gap in authored ground, no invisible catch. If a fall-out recovery
mechanism for `Character`/`Player` is wanted later, it belongs in Java (mirroring the vehicle
reclaim pattern), not as a physical Blender-authored floor.

## 5. Highways / railways / bullet train (overlay convention — SEPARATE files, never embedded)

Long-span connective structures (an expressway ring, elevated rail, a shinkansen line) are
**their own `.blend` files outside any district** — `assets/world_source/pieces/<Name>.blend` —
**never embedded in the district blends**. The reasons are structural, not stylistic:

- **They cross many district cells.** Embedded, a single track would be sliced into up to 6
  independently-regenerated files that must agree at every seam — exactly the cross-district
  coupling this pipeline removed. As one overlay file, the entire line is authored (and curved,
  banked, elevation-profiled) continuously in one place.
- **Different lifecycle.** Hand-editing a district must never touch the highway; an overlay edit
  must never force a district rebuild. Separate files = separate build loops.
- **Different residency.** A rail/highway is visible from far away and carries its own traffic;
  it wants a long-span, wide-radius `WorldZoneMarker` of its own (a normal streamed piece, just
  with `load_radius`/`unload_radius` tuned well past its own half-extent so it never unloads
  mid-span) — not chopped to the 504 m district streaming grain.
- **A train is not per-district content.** A vehicle that traverses the whole map needs one
  continuous route; per-district route fragments would need seam chaining for something that
  never behaves per-district.

The conventions (established by the first such piece, the Rainbow Bridge, `Piece_2_3_b` — a
**freestanding piece**: registered in `pieces.json`/`lib/piece_registry.py` like any other, just
not part of the 6×6 grid walk, §4's "freestanding" pieces):

- Authored in **world coordinates** (like the master's own content), exported with the same
  `blender/tools/export_world.py` + WorldBaker path to its own `.tscn` under
  `src/main/resources/com/openworld/world/districts/` — every piece bakes to the same output
  directory now, grid or freestanding (`build_piece.sh` handles both uniformly).
- Districts don't know about freestanding pieces; one touches down via its own ramp/pillar
  geometry over a district's ground (pillars carry their own `-colonly`). Author the touchdown
  against the real district content via `link_neighbors.py --master=<OverlayColl>` linking or
  `build_debug_preview.py`.
- Traffic on a highway overlay = its own `lane_*`/route layer inside the overlay blend, joining
  the arterial graph at ramp junctions (Roads & Traffic v2 Phase 3 — see PLAN.md). A train is a
  single long (probably looped) route of its own with one scripted vehicle, not ambient traffic.

### Editing a freestanding piece alongside a district (touchdown ramps, roads)

A freestanding piece can be pulled into a Blender session together with the district(s) it
touches down on, exactly like two districts sharing a seam (§4's "When you already know exactly
which 2-4 districts need a seam fixed"/"open_district_group.py" — both tools accept a **mix** of
grid and freestanding piece ids now, resolved through the registry):

```bash
cd assets/world_source
blender --background --python blender/tools/open_district_group.py -- \
    _edit_rainbowbridge Piece_2_3_b Piece_5_0
```

Or the whole-world session (§4 "One file for the whole world") already includes every
freestanding piece automatically — open it once and edit the bridge and any district in the same
file, no separate step needed. From the addon panel: type the piece id (e.g. `Piece_2_3_b`) into
"Other Pieces" alongside a district's own id, then "Open Group" (or "Add District(s)" to pull it
into an already-open group session) — the field accepts either kind.

The freestanding piece's content is **not shifted at all** when appended (it's already authored
in true world space, unlike a district's per-file local origin) — so a district and the piece land
at their real, correct relative positions automatically, and you can build/adjust the ramp's road
pieces (`ops_intersection.py`/`ops_segment.py`, same tools as any district) directly against the
district's real ground/road geometry, both visible and editable together in one viewport. Write
back the same way (`blender/tools/writeback_district_group.py`, or the panel's "Write Back Group") — each
item is un-shifted back to its own frame (zero offset for the freestanding piece) and saved into
its own `.blend`; a touched district still rebuilds + seam-checks against its *district*
neighbours as usual, a freestanding piece rebuilds via the same `blender/tools/build_piece.sh`
(never seam-checked — freestanding pieces have no `.seam.json`).

**How the road connection itself actually works — no special "ramp junction" step needed for
basic connectivity.** Lane connectivity is **geometry-derived at Godot runtime**
(`LaneGraph`/`VehicleAIController`, §7): any two lanes anywhere in the world whose *baked
endpoints* land within `JUNCTION_RADIUS` (4.5 m, `blender/lib/lane_kit.py`) of each other connect
automatically, regardless of which piece or file built them. `blender/tools/check_lanekit_connectivity.py`
already explicitly documents the district↔freestanding-piece case as one of the two connectivity
checks it supports — so the actual workflow is:

1. Build the ramp's road pieces in the freestanding piece (or the connecting street in the
   district) so the lane spine's end lands exactly where you want the touchdown, using the real
   neighbour content visible in the same scratch session (above) to place/snap it precisely.
2. `blender/tools/save_lane_kit.py` on **both** files to produce/refresh each one's
   `.lanekit.json` sidecar.
3. `blender/tools/check_lanekit_connectivity.py pieces/Piece_2_3_b.lanekit.json
   pieces/Piece_5_0.lanekit.json` — confirms `paired` (not `isolated`/`ambiguous`) at the
   touchdown before you bake either side. Both sides' offsets default automatically to their own
   registered `position` in `pieces.json` (`--offset-a`/`--offset-b` only needed for a hand-named
   test file that was never registered).
4. Bake both (`blender/tools/build_piece.sh` for each) — that's it. No junction registration, no
   explicit "connect lane A to lane B" step exists or is needed for a car to drive through cleanly.

**What genuinely isn't built yet** (Roads & Traffic v2 Phase 3, PLAN.md — a separate, later
concern from basic drivable connectivity above): a real junction arbiter (FCFS grant sets, timed
signals) for *complex* multi-way convergence at a ramp, and highway-specific traffic weighting/
speed limits. Until then, `VehicleAIController`'s existing junction throttle-clamp (§7,
`junctionThrottleScale` near any chained lane end) already applies uniformly, overlay or district
— cars slow down approaching the touchdown the same way they do at any tight turn, so the ramp is
drivable today, just not signal-arbitrated.

### The freestanding-piece build loop (bake-only, mirrors the district loop, §3)

The bridge, `pieces/Piece_2_3_b.blend`, has two collections — `OVERLAY` (its generated content,
originally built by a one-time generator script, now permanent/hand-owned like everything else,
§2 — that generator was removed once it had produced the bridge) and `MANUAL` (your hand-tuning
channel — seat/scale fixes, ramps, extra piers with `-colonly` proxies). Shared seat coordinates
(the bridge's `BR_*`/`ISL_*` constants) live in `blender/lib/world_grid.py` so the master
blockout, `slot_` anchors, and the bridge's own content agree.

```bash
blender/tools/build_piece.sh Piece_2_3_b   # bake-only, after hand-editing the .blend -- same
                                            # command as any other piece now
```

**Residency:** a freestanding piece is a **normal streamed piece** — `build_world.py` emits a
`WorldZoneMarker`/`RegionConfig` for it exactly like a grid district (no kind branch, §4's "One
file for the whole world"), just with `load_radius`/`unload_radius` deliberately widened past its
own half-extent (`half_extent + 300` / `+300` hysteresis for the bridge) so it stays loaded for
its whole length instead of unloading mid-span. There is no permanent scene node to wire up —
rebuilding the master (`build_world.sh`) picks up its registered position/radii automatically,
same as any other piece.

The bridge: the real PLATEAU span (joined to one mesh) + the `-colonly` road/rail decks and piers
that used to be the master's preview-only HARBOR blockout (which never shipped; the blockout
boxes were removed from `build_world.build_harbor`, the `slot_rainbowbridge` anchor stays as the
coordinate record).

## 6. PLATEAU data (historical — the extraction/import tooling no longer exists)

`plateau/extract_plateau.py` and `blender/lib/plateau_import.py` were removed along with the rest of the
generation pipeline (§2) — every PLATEAU-derived district, overlay asset, and building asset had
already produced its permanent output `.blend` (§2's list), so the extraction/import code that
made them had done its one-time job and nothing in this pipeline reads raw PLATEAU/CityGML data
anymore. This section is now purely the historical record of how existing terrain got here, kept
for context (and as a starting point if an importer is ever rewritten from scratch):

- Fresh extraction used to run `extract_plateau.py --precinct <name> --lon … --lat … [--dem <dirs>]`
  → `plateau/data/<precinct>.json` (buildings/roads/terrain in district-local metres) against raw
  CityGML living outside the repo (`/data/danilko/plateau_model/`) — see `plateau/ATTRIBUTION.md`
  for the data source attribution, which still applies to every already-imported asset.
- **Terrain-as-ground rule that was applied** (useful context for reading existing terrain, not
  an active rule anymore): if the stored terrain fully covered the district square
  (`terrain_covers_square`), the real DEM mesh became the ground. Districts with partial or no DEM
  coverage have no flat safety plane underneath (`add_ground_safety_plane()` was removed
  separately — see "No world-spanning safety floor" below) — a gap in the original DEM extraction
  is a real gap in that district today, not silently patched.

## 7. Roads, lanes, intersections & ambient traffic (road_kit_authoring)

> **Replaced (2026-07-27, road_blender_godot.md Phase 6):** the old generator-driven pipeline
> (`blender/lib/road_graph.py`, `blender/tools/save_roads.py`/`gen_roads_only.py`, hand-drawn `road_*` centerline
> curves + a `.roads.json` sidecar) has been removed entirely — no dual-path, no backward
> compatibility, every district regenerates through the addon below. See `road_blender_godot.md`
> Phase 6 (P6.1-P6.8) for the full migration history/design record.

Roads are built as **mesh-first pieces** with the `road_kit_authoring` Blender addon (dev-install:
`blender/addons/road_kit_authoring/README.md`), not drawn as bare centerlines. Three piece types —
intersections, straight/curved segments, lane-count transitions — each carry the geometry AND a
permanent "how was this built" record as native Collection custom properties (`rka_*`, editable in
Blender's own Custom Properties panel, survives file close/reopen). `blender/lib/intersection_kit.py`
(pure Python, no bpy, self-tested — `python3 blender/lib/intersection_kit.py`) is the closed-form geometry
underneath every piece: corner-fillet junctions from a list of approach-arm angles, per-lane
offset segments from an arbitrary spine, lane-count tapers.

**The authoring loop:**

1. Open a district `.blend`. Use the addon's Sidebar (`N`) panel to build intersections
   (`Build Intersection`, presets 4-way/3-way-T/3-way-Y/N-way) and segments (`Build Straight
   Segment`, or `Extend From Arm`/`Extend From Port` off an existing piece's own marker/port —
   snaps zero-gap by construction). Drag a piece's own marker Empties to reshape it live
   (`live_edit.py`'s `depsgraph_update_post` handler rebuilds in place).
2. Collect every piece in the open `.blend` into one combined sidecar:
   ```bash
   blender pieces/<piece-id>.blend --background --python blender/tools/save_lane_kit.py
   ```
   Writes `pieces/<piece-id>.lanekit.json` next to the `.blend` (same tool works unchanged for
   any registered piece, grid district or freestanding). Prints an authoring-time connectivity
   lint (`blender/lib/lane_kit.py`): `paired` (clean 1:1 connections), `isolated` (a dangling end —
   informational, a network boundary is legitimate), `ambiguous` (3+ candidates within
   `JUNCTION_RADIUS`, needs a look). Two pieces in DIFFERENT files (e.g. two neighboring
   districts) can be cross-checked the same way with `blender/tools/check_lanekit_connectivity.py
   <a>.lanekit.json <b>.lanekit.json`.
3. Rebuild (`blender/tools/build_piece.sh <piece-id>` — handles every piece uniformly now) —
   `bake_one()` auto-detects the `.lanekit.json` sidecar and wires it into `WorldBaker` as
   `lanekit_path`, no separate flag needed. Each lane becomes a native `Path3D`/`Curve3D`-backed
   `PathLaneRoute` (same `Lane` interface `VehicleRoute` implements — `LaneGraph`/
   `VehicleAIController` are fully polymorphic, so connectivity across pieces/files is
   **geometry-derived at runtime**: any two lanes whose baked endpoints land within
   `LaneGraph.JUNCTION_RADIUS` of each other connect, regardless of which piece/file built them).

   **One-click shortcut for steps 2-3** on a `District_<theme>_<gx>_<gy>.blend`: the panel's
   "Godot Export" box (top of the Sidebar) runs both commands for you in the background (a modal
   timer, so Blender's UI stays responsive for the ~20-40s bake) — watch the System Console for
   progress. Only enabled for a district saved in that exact stem form; an overlay or anything
   else still uses the two commands above by hand.

**Collision:** every piece already exports its own `-colonly` collision alongside the visual mesh —
`junction_pad` footprints (`kit_common.colonly_polygon`) and every `curb_loop()` (straight/curved
segments, lane transitions, per-corner intersection curbs, via `kit_common.colonly_swept`). This is
generated automatically by the normal build/rebuild operators; nothing extra to author. It is
**deliberately a separate mesh from the district's ground/terrain collision, never merged into it**
— roads (authored/regenerated via this addon) and ground (PLATEAU terrain, re-extracted from DEM
per district) change on independent schedules, and Godot's physics doesn't need one watertight mesh
for two overlapping static colliders to work correctly. Editing a road never requires touching the
ground mesh, and re-extracting terrain never requires re-authoring roads.

**Curb style, after the fact:** the panel's "Curb Style" button row (Left/Right ×
None/Box/Gutter/Asset, shown when a segment or lane-transition piece is active/selected) changes
curb style on an already-built piece and rebuilds in place — a persistent alternative to the build
operator's own F9 redo panel, which stops applying the moment any other action runs. For an
asymmetric ASSET curb mesh (authored to attach on one side only), use the SAME asset collection on
both Left and Right — the addon automatically spins the right-side row 180° (`curb_asset_rot_offset_r`)
so it still faces the correct way; no separate right-side asset or two-level gutter+curb split needed.

**Ambient traffic + zones:** every combined lane is tagged `zone_id` (the `.blend`'s own stem by
default, overridable per-piece via a manually-added `rka_zone_id` custom property) — a district's
master region marker sets `traffic_route` to that exact stem, matched by
`WorldZoneManager.findRoute`'s zone-id-equality pass (checked before its legacy name-prefix scan,
which still exists only for hand-authored `VehicleRoute` content that never went through this
pipeline). Re-run the master build (`blender/tools/build_world.py`) after a district's first
`.lanekit.json` lands so the region marker's meta picks it up.

**Debugging:** F4 (`DebugHarness`) drops one AI car on every route in the scene (works in
`SoloPiece.tscn`); `WorldZoneManager.debugLog` prints per-zone `N cars, M moving, K routed`
(routed-but-0-moving = falling through missing ground); F3 (`RouteDebugOverlay`) renders every
`VehicleRoute`/`PathLaneRoute` in the scene, colour-coded.

## 8. Placing water & other gameplay objects (in Blender — never edit the baked .tscn)

Everything gameplay-flavoured is placed in the `.blend` as a **named object**; the WorldBaker
converts it by name. Hand-editing a baked `.tscn`/`.scn` is always wrong — the next bake
overwrites it. Put hand additions in `MANUAL` (survives regen, §2); the full name → node table
is in `BLENDER_CONVENTIONS.md` (I6a), the common ones:

| You place (Blender) | Becomes (Godot, at bake) |
|:--|:--|
| Empty `water_<id>` scaled/parented over a box (or with `size` custom prop) | `Area3D` in group `"water"` (swim volume) |
| Empty `spawn_<faction>_<n>` (+ `count` prop) | ambient-AI `SpawnConfig` on the zone |
| Empty `instance_<AssetId>` or any object with `asset_path = res://…` prop | scene **instance** of that asset (own collision/scripts) |
| `mmesh_<piece>` markers (generated, but same idea) | one `MultiMeshInstance3D` per asset |
| Mesh named `<Name>-colonly` / `-col` / `-convcolonly` | collision (invisible / visible / convex) |
| `road_kit_authoring` piece (+ combined `.lanekit.json` sidecar, §7) | `PathLaneRoute` lanes + junctions |

So: **water = drop a `water_<id>` marker in the blend and re-bake** — no `.tscn` editing. Same
for any future volume/marker type: add a prefix to the WorldBaker table once, then it's pure
Blender authoring forever.

## 9. Navigation (pedestrian navmesh) — what it's for, known warnings

- **Cars never use the navmesh** — they follow the explicit lane graph (§7). A navmesh has no
  lanes/direction, so it can't drive traffic; don't try.
- **Pedestrian AI uses one baked `NavigationRegion3D` per district**, baked by `NavBaker` from
  the district's own collision as part of `build_piece.sh`. This is the right tool here: AI must
  path around arbitrary real PLATEAU building layouts, which grid/waypoint graphs handle worse
  for more authoring effort. Alternatives only pay off elsewhere (flow fields for 100+-agent
  crowds; nav links for jumps/ladders — Godot supports those *on top of* the navmesh anyway).
- **"Navigation region synchronization had N edge error(s) / more than 2 edges tried to occupy
  the same map rasterization space"** — Godot merging the loaded navmeshes found coincident
  edges: typically two loaded districts' meshes meeting exactly at a seam, or coplanar surfaces
  (road slab on terrain) baked into one mesh. It is a **warning, not a failure** — the duplicate
  edge connection is dropped, agents still navigate. Act on it only if AI visibly stall at a
  border; remedies, in order: raise the bake `cell_size` in `NavBaker`, lower
  `navigation/3d/merge_rasterizer_cell_scale` (project settings), or silence it via
  `navigation/3d/warnings/navmesh_edge_merge_errors`. Districts abut by design, so occasional
  seam-edge merges are expected background noise.

## 11. Cross-district GPS & race courses (conventions — design notes, R2 not yet implemented)

The structural fact everything here follows from: **district content streams** (its
`VehicleRoute`/`PathLaneRoute` lanes register/deregister with `WorldZoneManager` on tree
enter/exit; anything baked into a district `.tscn` vanishes on unload), while the **ARTDECK
collision deck is always resident** in the master (P6.8: the old arterial LANE backbone over
that deck was removed — see §7 — so today the deck is collision-only; an overlay, §5, is the
always-resident place for a real map-spanning lane network, e.g. a highway). Cross-district
features must lean on the always-resident layer or on pure data — never on live nodes inside a
district that might not be loaded. **There is no world-spanning safety floor anymore** (removed —
see "No world-spanning safety floor" in §4) — ARTDECK only guarantees ground under the ~21 m
backbone strips themselves, nothing wider, so a cross-district feature that needs "ground
guaranteed everywhere regardless of streaming" can no longer assume that; it must either stay on
the ArtDeck-covered backbone or keep the districts it passes through loaded.

### GPS

- **Today (I5, done):** the waypoint is a world-XZ position in `WaypointStore`, drawn by
  radar-style widgets (minimap blip clamp + crosshair arrow). Nothing is per-district, so it
  already works across the whole map — straight-line guidance only.
- **Turn-by-turn upgrade (planned):** do **not** pathfind over live `VehicleRoute`/`PathLaneRoute`
  nodes — unloaded districts have none. Every district's `.lanekit.json` sidecar (§7,
  `blender/tools/save_lane_kit.py`) already holds its junction/lane graph as engine-free JSON at build
  time; bake all of them into one always-resident manifest resource and A* over it: an overlay's
  lanes (§5, e.g. a highway) give the inter-district legs, a district's own combined sidecar
  refines the first/last mile — the same "prefer a highway/overlay path when one exists, else
  district-to-district local roads" preference recorded in road_blender_godot.md P6.5. Draw the
  result as a minimap polyline. (PLAN.md I6 note: Blender-authored waypoints ride the same bake
  path.)

### Race courses (R2 design, PLAN.md)

- **Checkpoints must not stream.** A `race_<id>_<idx>` empty baked inside a district `.tscn`
  disappears mid-race when that district unloads. A cross-district course therefore lives in an
  **overlay** (§5 — exactly the "long-span content that must never chop at the 504 m grain" case,
  same precedent as highway/train), or `RaceDirector` holds checkpoint *positions as data* and
  spawns the `Area3D`s itself for the race's lifetime.
- **AI racers on the arterial backbone itself survive unloaded districts** because ARTDECK's
  collision strips are always resident — an arterial-backbone race works with zero streaming
  concern. A race line through district *interiors*, or any point off the ArtDeck strips, now has
  **no** ground guarantee at all (the world-spanning safety floor that used to cover this gap was
  removed — see §4) — those districts must stay loaded for the race line to have ground under it;
  racers cluster near players so proximity streaming mostly covers it; the safety net is a small
  `RaceDirector` → `WorldZoneManager`
  "pin these zones while the race runs" extension.
- **The AI racing line is the same authored-curve pipeline** — a `VehicleRoute` drawn along the
  course (in the race overlay for cross-district courses), driven by `VehicleAIController`
  verbatim. Replication is host-authoritative checkpoint grants over the existing world-event
  seam.
